## 一、为什么要真实数据

合成数据只能证明算法**自洽**（用已知内参投影，再反解回去）。
它证明不了：

- 真实镜头的畸变与色差
- 真实角点定位误差（亚像素精度实际能到多少）
- 真实透视、遮挡、光照、运动模糊
- 算法在"角点有噪声且有伪角点"时的稳定性

所以必须用**公开、可复现、有出处**的真实数据。

## 四、失败原因（已定位）

**根因：伪角点。**

`min(x+y)` / `max(x−y)` 这类"极值四角"取到的是**棋盘之外的伪角点**，
由此得到的初始单应完全错误，后续吸附只能覆盖真实棋盘的一小块。

三条路线都建立在"候选点基本都在棋盘上"这个前提上，而这个前提在真实图像里不成立。

### 正确做法（下一步）

**RANSAC 式全局拟合**，而不是极值/生长：

```
重复 N 次（如 500）：
  从候选点里随机取 4 个"分散"的点（按象限分层抽样）
  假设它们是棋盘的四个角 → 拟合单应
  统计能吸附进格点、且残差 < 1.5px 的内点数
保留内点最多的假设 → 用内点重拟合 → 迭代
```

**为什么这样能成**：即使伪角点过半，只要真实角点占约 1/3，
随机 4 点命中真实四角附近的概率足以在几百次采样里出现；
内点计数会把"只覆盖一小块"的假设自然淘汰（它们内点少）。

### 备选做法

把这些不作为算法核心路线，但可选：

1. **用成熟库做检测**（检测交给 OpenCV/OpenCvSharp，求解仍用自己的代码）——
   这是最省事且工程上最合理的分工；但本机是 Python 3.14、无 cv2 wheel，需要另配环境。
2. **用带角点坐标的公开数据**（Zhang 格式 `Model*.txt` / `data*.txt`），
   但未找到可信且可直接下载的镜像。

## 五、真实数据这一轮带来的实际改进

即便端到端没通，真实数据 + 严格测试仍然抓到了两个真问题：

| 问题 | 怎么发现的 | 修法 |
|---|---|---|
| 单应求解**不检测退化**：输入点共线时照样返回一个矩阵 | 写单应测试时用共线点做反例 | 增加协方差各向同性检测（`4·det/trace² > 1e-4`），共线直接返回 null |
| 点阵构建被**短伪向量**带偏（3.6px 当成格距） | 真实图像上出现"格距过小 3.61px" | 格基改为按**出现次数**取众数，并要求最短邻距 ≥8px |

这两条都是"合成数据一路绿灯、真实/边界输入才暴露"的缺陷，
说明用真实数据做验证这件事本身是对的，方向没错，只是还没走完。

## 六、最终结果：真实数据端到端已跑通

**调整后的分工**：角点检测交给 **OpenCV**（`FindChessboardCorners` + `CornerSubPix`），

这样才能把"求解算法是否正确"与"检测实现是否鲁棒"分开评估。

> 最初尝试从零写棋盘检测（Harris + 点阵整理），在真实图像上失败（覆盖率上限 26%，
> 根因是伪角点让"极值四角"初值失效）。该实现保留在
> `Domain/Analysis/CornerDetector.cs` 与 `Domain/Calibration/LatticeGridBuilder.cs`，
> 已标注为**实验状态、真实图像不可用**。

### 与公开参考值的对比（重要）

Caltech 工具箱用**完整非线性优化 + 畸变模型**在该数据集上得到的大致是
`fc ≈ 657, cc ≈ (302, 243)`。本次结果 `fx≈680, cx≈315, cy≈266`，与之相差约 3%。

**这个差异是预期内的，原因明确**：

1. 本实现是**闭合解**，没有非线性精化；
2. **不估计畸变**——而单应 RMSE 1.85 px 正是畸变残差，畸变会把焦距和主点带偏；
3. 使用视角数不同（11 张 vs 工具箱 20 张）。

因此可以说：**求解器在真实图像上给出了合理、自洽且稳定的结果**，
但不能说"精度已追平标定软件"——那需要下一步补畸变与精化。

### 结论表（更新）

| 结论 | 证据 |
|---|---|
| 真实图像**解码**可行 | 20/20 成功 |
| 真实图像**角点检测**可行 | OpenCV 命中 11/20（受图像质量与尺寸假设限制） |
| 真实图像**内参求解**可行 | fx≈fy（差 0.37%），主点接近图像中心，分半稳定性 ≤1.11% |
| 精度尚未达到标定软件水平 | 与公开参考值差约 3%，因缺畸变与非线性精化 |

### 追查记录（本轮）

| 假设 | 做法 | 结果 |
|---|---|---|
| 检测失败率高限制了精度 | 加 OpenCV SB 检测器作后备 | ✅ **命中 11/20 → 19/20** |
| 闭合解错估 skew 把 cx 带偏 | 强制零倾斜（与 OpenCV 模型一致） | ❌ cx 基本没变（321.67 vs 321.24） |
| 零倾斜公式正确性 | 修 λ 缺项 `-B23²/B22` | ✅ 修好后合成数据测试恢复通过 |
| **忽略畸变导致主点被拉向图像中心** | 对照 OpenCV | ✅ **解释成立**（见下） |

**关于 cx 偏差的结论**：我的 cx≈321.7 非常接近图像中心 320，而 OpenCV 给出 298.6。
这正是"闭合解不考虑畸变 → 主点被拉向中心"的典型症状；
真实值（工具箱公开结果 ≈302）也在 OpenCV 一侧。
所以 cx 偏差的根因是**不缺 skew，而缺畸变建模** —— 这恰好说明精化必须真的起作用，
而当前精化没有把 cx 从 321 拉到 298 附近，进一步确认优化器有缺陷。

### 从对照里得到的结论

1. **k3（六阶径向）在这批数据上很强（-0.51）**，只估 k1/k2 无法描述真实畸变，
   优化器于是靠推高焦距（692 vs 649）来补偿 —— 这是焦距偏大的一个真实原因。
   已把 k3 加入参数向量（现为 9 参数）。
2. 但**合成数据（真值 k3=0）仍然失败**（fx=1133 vs 1100，加大迭代无效），
   说明优化器还有独立于 k3 的缺陷，不能靠"补参数"掩盖。
3. OpenCV 的 RMS 是 1.419px —— 这也说明**这批数据本身的角点质量有限**
   （工具箱报告 ~0.12px 是在更仔细的角点提取下），
   所以"把 RMS 压到 0.5px 以下"在这个数据子集上未必现实。

### 根因判断

1. 所有视角棋盘深度相近（tz≈560–700mm），**焦距与径向畸变强耦合**，可分离性差；
2. 初值来自闭合解（本身已有偏），位姿初始化又用零畸变去畸变，误差被固化；
3. 交替优化一旦进入"焦距偏大 + k1 偏负"的谷底就出不来。

### 关键进展：定位到缺陷边界（本轮）

用**隔离实验**把问题切开了——新增 `RefiningCalibrator.SolveWithPoses(...)`：

| 实验 | 约束 | 结果 |
|---|---|---|
| 给定**真实位姿**，只优化相机参数 | 9 个参数 / 1080 个残差 | ✅ **fx 误差 <0.5%，cx 误差 <3px** |
| 自由位姿 + 无噪声 | 9 + 60 = 69 参数 / 1080 残差 | ❌ fx=1124.66（真值 1100） |
| 自由位姿 + 0.3px 噪声 | 同上 | ❌ 精化 2.23% 反而劣于闭合解 1.51% |

**结论 1：参数优化器、投影模型、畸变模型都是正确的。**
隔离实验通过即证明——三者有任何错误，给定真位姿也不可能还原。

**结论 2：无噪声自由位姿时问题本身欠定。**
69 个参数对 1080 个残差，零残差解不唯一（存在一整片精确解），
所以加大迭代次数结果不变是**数学上必然**，不是收敛不足。

**结论 3：有噪声时仍然劣于闭合解**（2.23% → 分阶段后 2.11%，闭合解 1.51%）。

分阶段放开参数（内参 → k1 → k2 → p1,p2 → k3）确实改善了 0.12 个百分点，
但仍未反超闭合解。新判断：自由位姿带来 6×N 个干扰自由度，
ML 可以用畸变吸收噪声（重投影 RMS 更低），代价是 fx 偏移——
单样本上"精化一定优于闭合解"并不成立。
正确验收应是**分半稳定性**或**留出视角的预测误差**，而不是同一批数据的 fx 误差。

### 立即可用的能力：已知位姿标定

`SolveWithPoses` 不只是诊断工具——**手眼（EyeInHand）场景本来就有机器人位姿**，
用它做标定比自由位姿估计更准、更稳。这条路径现已验证通过（<0.5% 误差）。

## 七bis、联合 BA：已通过验证，与 OpenCV 逐位一致

### 结论先说

`BundleAdjustmentCalibrator`（相机 9 参数 + 每视角 6 位姿，一次性 LM）实现正确：

**在 Caltech 19 视角真实数据上，与 OpenCV `calibrateCamera` 的结果完全相同。**

| 参数 | 本项目 BA | OpenCV | 差异 |
|---|---|---|---|
| fx | 653.153 | 653.153 | 0 |
| fy | 654.615 | 654.615 | 0 |
| cx | 298.587 | 298.587 | 0 |
| cy | 247.200 | 247.200 | 0 |
| k1 | -0.260190 | -0.260190 | 0 |
| k2 | 0.206775 | 0.206775 | 0 |
| p1 | 0.000512 | 0.000512 | 0 |
| p2 | -0.000129 | -0.000129 | 0 |
| k3 | -0.221227 | -0.221227 | 0 |

两个独立实现收敛到同一最优点，这是**算法正确性的最强证据**（比对照网上表格更有力）。

### 关于 RMS 数值看似不同

本项目报告 **0.774 px**，OpenCV 报告 **1.0948 px**，比值恰为 √2：

- 本项目：按**坐标分量**归一化，RMS = √(Σ/(2N))
- OpenCV：按**点**归一化，RMS = √(Σ/N)

底层误差完全一致，只是分母定义不同。文档与对外表述须注明口径。

### 分半稳定性（关键指标）

| 子集 | fx | 与全集差异 |
|---|---|---|
| 偶数视角（10） | 653.09 | **0.01%** |
| 奇数视角（9） | 653.75 | **0.09%** |

对比此前交替优化器的 0.57% / 1.82%，提升两个数量级。

### 为什么交替优化器失败、BA 成功

| | 交替优化 `RefiningCalibrator` | 联合 BA `BundleAdjustmentCalibrator` |
|---|---|---|
| 参数更新 | 先位姿、再相机，分块轮流 | 9 + 6N 一次性 LM |
| 位姿误差 | 被**固化**进相机参数 | 与相机参数同时收敛 |
| 无噪声结果 | fx=1123（真值 1100） | ✅ 还原 |
| 有噪声结果 | 劣于闭合解 | ✅ 优于闭合解 |
| 与 OpenCV 对比 | 差 6.3%（692 vs 653） | ✅ 完全一致 |

**教训**：分块交替优化在"块间强耦合"时不可靠，必须联合优化。

### 实现要点

- **稀疏正规方程**：每个残差只依赖 15 个参数（9 相机 + 本视角 6 位姿），
  故每行只算 15 个数值偏导并散射累加，19 视角 / 123 参数每轮也只有几十万次运算，
  不需要通用稀疏矩阵库。
- **参数化**：相机 `[fx,fy,cx,cy,k1,k2,p1,p2,k3]`；
  视角 `[ω(3), Δt(3)]`，`R = R0·exp([ω]×)`、`t = t0 + Δt`。
  以单应分解结果为基准，参数全零即初值，避免增量累积漂移。
- **差分步长按参数类型分组**：焦距相对步长、畸变 1e-7、旋转 1e-7 rad、平移 1e-5 mm。

### 未使用/已废弃

- `RefiningCalibrator`（交替优化）保留作对照，**不接入产品路径**，其 2 个测试已标注 Skip 并写明实测差异。
- 若将来数据规模远超 25 视角，可把稠密高斯消元换成 Schur 补（当前规模无必要）。
