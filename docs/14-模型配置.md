# 14 · 模型配置（多套并存 · key 只增删 · 自动识别模型与强度）

> 目标：填个 baseurl + key 就能用，不再手敲模型名。

---

## 一、baseurl 是什么

**模型服务的入口地址**：决定 key 送到哪儿、模型清单从哪儿拉。

| 你填 | 实际使用 |
|---|---|
| `api.deepseek.com` | `https://api.deepseek.com/v1` |
| `https://api.openai.com/v1` | 原样 |
| `https://example.com/openai/v1` | 原样（已有路径不猜） |
| `localhost:11434` | `http://localhost:11434/v1` |
| `192.168.1.50:8000` | `http://192.168.1.50:8000/v1` |

规则（`LlmSettingsStore.NormalizeBaseUrl`）：

1. 缺 `https://` / `http://` 时自动补；
2. **本机与内网地址（localhost / 127. / 10. / 192.168. / 172.16.）默认 http**，其余默认 https；
3. 路径为空时补 `/v1`；已带路径则原样保留。

## 二、多套配置并存

数据结构：`LlmSettings.Profiles[]` + `ActiveProfileId`。

- 可以同时存 DeepSeek / OpenAI / 私有部署，界面下拉切换；
- 第一条自动成为当前配置；删除当前配置后自动回退到剩余第一条；
- 切换**立即生效**：`RoutingLlmProvider` 每次调用比对配置签名，变了就重建 provider
  （否则会继续用启动时那套，用户会以为"切换没用"）。

## 三、key：加密保存，只能增删，不能修改

| 操作 | 是否允许 |
|---|---|
| 新增配置时写入 key | ✅ |
| 查看明文 key | ❌ 任何接口都不返回 |
| 修改已有配置的 key | ❌ **没有这个入口** |
| 修改非密钥字段（名称/baseUrl/模型/强度） | ✅ |
| 删除整条配置（含 key） | ✅ 需二次确认 |

**为什么不做"编辑 key"**：一旦有编辑入口，就必须把旧值显示出来或让用户重填，
两种都会扩大明文暴露面。只允许多一次"删除 + 新增"，就能保证
**密钥只可能从"用户主动输入"这一条路径进入系统**。

存储：

- 密文走 **Windows DPAPI**（当前用户作用域）→ `ApiKeyProtected`；
- 明文永不落盘；换 Windows 账户或换机器后解不开，会提示"请删除后重建"；
- 另存一个 `KeyHint`（**只保留末 4 位**）用于人工辨认是哪把钥匙。

## 四、自动识别模型与强度

### 4.1 拉模型清单

`GET {baseUrl}/models`（Bearer key）→ 解析 `data[].id`。

拉不到时**不报错**，回退内置清单并在界面标明来源：

| 情况 | 处理 |
|---|---|
| 401 | 回退，提示"key 被拒绝" |
| 404 | 回退，提示"该服务没有 /models 接口" |
| 网络失败 | 回退，提示具体错误 |

> 很多"OpenAI 兼容"服务本来就没有 `/models`，直接报错会把这类服务完全堵死。

### 4.2 强度 = 模型分档 + 推理力度

**① 模型分档**（自动分类，用于界面分组与推荐）

| 档位 | 判定关键词（示例） |
|---|---|
| 快 Fast | mini / flash / lite / small / nano / turbo / haiku / 7b / 8b |
| 均衡 Balanced | 其余（含 deepseek-chat、gpt-4o） |
| 强 Strong | pro / max / ultra / reasoner / o1 / o3 / gpt-5 / opus / 70b / 405b |

**② 推理力度**（low / medium / high）

只有**明确支持** `reasoning_effort` 的模型才发送该参数：

- 发送：`o1*`、`o3*`、`o4*`、`gpt-5*`、名字含 `-reasoning`
- **不发送**：`deepseek-reasoner` —— 它自身就在推理，但**不接受这个参数**，传了会 400

> 这条区分很关键：**"是推理模型" ≠ "接受推理力度参数"**。
> 判断错了不是"力度没生效"，而是直接请求失败。

## 五、怎么用

### 界面（AI 标签页）

```
[当前配置 ▼]  [使用] [测试连通] [删除]      ← 切换 / 验证 / 删除（二次确认）
[新增] 名称 [ ] baseUrl [ api.deepseek.com ]
       模型 [ 拉取后可编辑 ▼ ] 强度 [低/中/高 ▼] key [******]
       [拉取模型] [新增配置]
```

- `拉取模型`：填了 baseUrl 就能拉，不需要先保存
- `测试连通`：发一个最小请求，明确告诉你 key 能不能用
- key 用 PasswordBox，只写不读

### 命令行

```powershell
# 看现有配置（标出当前使用的一条）
Agent --configure --list

# 新增一套（key 从 stdin 读，不进命令历史）
Agent --configure --add --name DeepSeek `
      --base-url api.deepseek.com --model deepseek-chat `
      --strength medium --api-key-stdin

# 拉取模型清单（失败自动兜底）
Agent --configure --models

# 切换 / 删除
Agent --configure --use   <id>
Agent --configure --remove <id>
```

## 六、旧配置自动迁移

旧版是单条扁平字段（`BaseUrl` / `Model` / `ApiKeyProtected`）。
首次读取时自动转成一条 profile，并**清空旧字段**（避免同一把 key 在两处存在）。

## 七、已知限制

| 项 | 说明 |
|---|---|
| 只支持 OpenAI 兼容协议 | Anthropic 原生 / Gemini 原生需另写适配器 |
| 推理力度参数名不统一 | 只对认得的模型发 `reasoning_effort`，其余不发并标注 |
| 未验证真实调用 | 本机没有可用 key；连通性靠"测试连通"按钮验证 |
| DPAPI 不能跨机迁移 | 换机器需重新输入 key（这是有意的安全取舍） |

## 八、常见问题（实测遇到过）

### Q1：拉取模型提示「key 被拒绝（401）」

先分清两种 401：

| 提示 | 真正原因 | 怎么办 |
|---|---|---|
| 「本次请求**没有携带密钥**（401）」 | 还没填/没保存 key | 先在「密钥」里输入，再拉取 |
| 「密钥被拒绝（401）——key 无效，或与该 baseurl 不是同一家服务」 | key 是错的，或地址指错了服务 | 核对 key 与 baseurl 是否配套 |

早期版本把这两种混成一句"key 被拒绝"，会把人引向错误方向。

### Q2：新增配置失败，`Access to the path '...\llm.json.tmp' is denied`

实测现场：

- 目录 ACL 正常（当前用户 FullControl）
- 没有残留 `.tmp`
- Defender「受控文件夹访问」是关闭的

→ 属于**瞬时占用**（杀毒软件/索引服务正在扫描刚创建的 `.tmp`），不是权限坏了。

现在写入做了三件事：

1. **重试 4 次**（间隔 30/60/90ms），多数情况第一次重试就成功；
2. 每次失败后**清理残留 `.tmp`**，避免下次被"已存在"卡住；
3. 仍失败时抛 `SettingsPersistenceException`，消息里包含**路径、尝试次数、原始异常类型**，
   并提示常见原因（安全软件锁定/被占用/权限不足）。

另外：`JsonSettingsStore` 构造时**不再因目录不可用而抛**——否则会变成"程序起不来"，
比"保存失败"更难查。

### Q3：提示「当前配置的密钥无法解密」

DPAPI 绑定当前 Windows 账户与机器。换账户/换电脑后会解不开——
这是有意的安全取舍，处理方式：删除该配置，重新新增并填入 key。
### Q4：连「随机名可写」都失败（Access denied 与权限无关）

实测现场（用户机器）：

```
原始错误：UnauthorizedAccessException / Access to the path '...\llm.json' is denied.
各策略结果：临时文件+替换 / 固定临时文件 / 直接覆盖 —— 全部被拒
现场诊断：目录存在=True；随机名可写=否；.tmp 后缀可写=否；用户=...（管理员）
```

而 `icacls` 显示该目录对当前用户是 `(I)(OI)(CI)(F)`（可继承的完全控制）。

→ **目录权限没坏，是外部拦截**：安全软件/EDR 按进程拦写入。
"随机名也写不了"是关键判据——它排除了"文件名规则"，指向进程级拦截。

处置顺序：

1. **程序已会自动换目录**：`LocalAppData` → `LocalAppData\CameraControl-Data`
   → `Roaming\CameraControl` → `ProgramData\CameraControl` → `TEMP\CameraControl`，
   选第一个**真正能写入**的（探针写文件验证，不只看权限位）。
   启动日志里的 `dataDirectory` 就是最终选择。
2. 把 `CameraControl.exe` 加入安全软件白名单（← 治本）
3. 用记事本往该目录另存一个 txt 做对照：
   - 记事本也失败 → 目录/系统层面问题
   - 记事本成功、程序失败 → 按进程拦截，走第 2 步
