## 一、为什么这些值必须实测

本系统的核心精度链条是：

```
相机像素当量 → 帧间位移测量 → 振动就绪判定 → 多相机同步 → 多视角融合
```

每一环都有阈值。阈值取自"经验"还是"实测"，直接决定融合精度是否可信。
在没有真实工位数据前，这些值统一标为**未验证**，且**不得对外声称是验证过的**。

## 三、待实测的**结论级**事项（比阈值更重要）

| 编号 | 待验证的假设 | 验证方式 | 若不成立的后果 |
|---|---|---|---|
| H-1 | **用相机自身做振动传感器可行** | baseline 噪声底换算 mm ≤ 融合精度目标的一半 | P2 视觉门不可行，需换镜头/减振/外部传感器 |
| H-2 | 软同步偏斜可接受 | settling 报告；对比硬触发 | 多视角融合出现系统性错位 |
| H-3 | 硬触发偏斜 ≤ 1ms（目标 100µs） | 多相机对拍闪灯/LED，比较帧间关系 | 融合精度不达标，需要更高端触发方案 |
| H-4 | 曝光/频闪预算能满足运动冻结 | 预算校验 + 实拍模糊量 | 动态抓拍不可用，只能退回静止采集 |
| H-5 | 工件表面纹理足以支撑亚像素测量 | 相关分数分布 | 位移测量不稳，需改用结构光/特征靶标 |

## 四、如何一次性采集验证数据

```powershell
cd tools\CameraControl.Tools.BurstAnalyzer

# ① 基线（机械臂完全静止 ≥5 秒）
dotnet run -- --mode baseline --frames 60 --out D:\temp\baseline.json

# ② 衰减（开始采集瞬间扰动机械臂）
dotnet run -- --mode settling --frames 80 --interval-ms 30 --out D:\temp\settling.json

# ③ 若已知像素当量与精度目标，可直接出可行性结论
dotnet run -- --mode baseline --frames 60 `
  --scale-mm-per-px 0.005 --fusion-accuracy-mm 0.1 `
  --out D:\temp\baseline-verdict.json
```

> 工具启动时会先跑自检；若以管理员身份运行会直接提示并退出（摄像头会被 Windows 拒绝）。

拿到这两份报告后，把对应数字填进 `ReadinessCriteria`，然后：

2. 更新本文件
3. 在 ADR 里记录"该阈值来源：实测报告 XXX.json，日期 YYY"
